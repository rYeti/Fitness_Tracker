# Changelog

Engineering record of what changed in each release. Newest first.

There is no length limit here. The short blurb users actually see on the store
listing lives in `PLAY_NOTES.md` — a release needs a section in both.

Work in progress goes under `## Unreleased`. The release workflow renames that
heading to the version it went out as, so a `## <version>` section is history:
it is what those users have, and nothing new belongs in it. See
`docs/android-release.md`.

## Unreleased

- Pinned `targetSdk` in `fittnes_tracker/android/app/build.gradle.kts` to 36 instead of leaving it delegated to `flutter.targetSdkVersion`. Delegated, the API level Play judges a release by was a property of whichever Flutter toolchain CI happened to resolve that day — invisible in the diff and impossible to review. The release workflow's preflight step now also logs the resolved target SDK for every run, and `docs/android-release.md` gained a section on actually promoting a build to the production track, since every release to date has gone to internal only.

## 1.0.2+15

- Chat messages are now end-to-end encrypted. Each account holds an ECDH P-256 key pair whose private half is generated on the device, kept in the platform keystore, and never sent anywhere; message bodies are encrypted with AES-256-GCM under a secret both parties derive from opposite halves of that pair. The API stores and forwards ciphertext it has no key for, so a database dump or a backup no longer exposes a single conversation. Messages sent before this change stay readable and are marked as version 0 — the server cannot encrypt what it was never given a key for, and inventing a key to backfill them would put it in the one place the feature says it must not be. There is no key backup by design, so reinstalling, or signing in on a second device, means messages from before that point cannot be decrypted there; those show as "Message can't be decrypted on this device" rather than as blank bubbles, and the same wording is what a screen reader hears. The private key deliberately survives sign-out, so signing back in on the same device keeps your history. See `docs/chat-encryption.md`.
- Chat push notifications no longer send message text to Google. The server used to put a 140-character preview into the FCM payload for the operating system to draw, which meant it had to be able to read the message. Push is now data-only: the payload carries the ciphertext and the recipient's own device decrypts it and raises the notification, so the lock-screen preview survives without the message ever leaving the two devices in readable form. The trade is real and worth knowing about — a data message is delivered to the app rather than to the OS, so Android may hold it under Doze or App Standby, and a force-stopped app receives nothing. A message too large for FCM's payload limit is left out entirely rather than truncated, because a ciphertext cut short fails its authentication tag; those arrive as the sender's name and "New message".
- The conversation list preview is now produced on the device instead of by the server, which can no longer read one. A thread whose last message this device cannot decrypt shows "New message" rather than claiming the conversation is empty.
- The workout builder's icon buttons are now labelled for a screen reader — edit day, delete day (each naming which one), the day editor's own Done, delete exercise and remove set (each naming which), the "add a day" FAB (naming Add vs. Close depending on whether the menu is open), and save on the single-workout editor. The delete button on every food row in a meal template, create or edit, now names the food it removes rather than announcing a bare "Delete".
- Fixed a silent crash opening a seeded workout for review: `ActiveWorkoutView` reads the first planned set the instant the screen builds, and a workout assembled without ever calling the sets endpoint has none — the screen painted nothing rather than a visible failure. The real app cannot produce this state; it was a gap in test data, not in the view.
- The set-history circle on the active-workout screen — tap it to mark a set as warm-up, drop set, failure, or left/right-only — now meets the 44×44 minimum tap target on mobile. It measured 32×32, its own visual scale, which was also the entire tap target for the primary interaction of the app, used one-handed mid-set.
- The join-trainer code entry screen has a desktop layout; its field and button were rendering full-bleed, 97.8% of a 1440px viewport.
- The coach-chat composer's attachment button (present, permanently disabled — there's no upload endpoint yet) reached a screen reader as an unnamed button despite carrying a visible tooltip. A `Tooltip` wrapped around a disabled child doesn't merge its label into the child's semantics node on Flutter web; switched to the button's own `tooltip:` parameter, which does.
- Fixed coach chat being unreachable in review/test builds: the seed's two trainee accounts were never linked to a trainer, so the card that opens it never rendered. Not an app defect — the previous note calling this a possible one was wrong; see `docs/frontend-design-review.md` section 14 for the correction.
- Added `store/` — the App Store and Google Play listing package: subtitle, promotional text, short description, long description, ASO keywords, and six store screenshots. Every claim in the copy is traced to a symbol in this repo rather than to a memory of the app, and doing that turned up two places where the app's own copy contradicts the app's own behaviour: the paywall advertises CSV export as a Premium feature but none of the four export tiles in Settings is wrapped in `PremiumGate`, so a free user gets their CSV; and `PremiumGate` wraps the rest-timer *switch* rather than the timer, whose preference defaults to true and is read with no entitlement check, so free users get the rest timer and cannot turn it off while paying users get the ability to turn it off. Neither is fixed here — each is a one-line change and the two possible fixes are opposite, so both need a product decision. The listing describes the shipped behaviour in both cases.
- The screenshots are captured from the running app and then framed. `store/screenshots/capture-app.mjs` drives the built Flutter web bundle in a browser, signs in through the real login screen as the account `e2e/tools/seed-review-data.mjs` seeds, and photographs seven screens at both stores' phone sizes; `compose.mjs` wraps six of them in a headline band and a device bezel, which is what gets uploaded. The two steps stay separate so the bare captures remain in the repo as evidence that the artwork contains real app pixels — nothing in the compositing step redraws a screen. `store/screenshots/README.md` is the runbook for the Postgres/API/seed/build stack it all needs. An earlier revision shipped hand-written HTML mockups of the app instead, which was wrong: held against the running app they had the theme, the tab count, the dashboard's cards and the entire set-logging flow wrong — the app logs one set at a time through a stepper, not a table. Three things the capture path turned up and now encodes: the app throws `Incorrect locale information provided` and never mounts if the browser's locale is one `intl` cannot parse, which surfaces only as a boot timeout; the Dashboard must be shot after other screens because its aggregates are only correct once `SyncService.pullAll()` has landed, and shooting it first photographs zeroes on a populated account; and a pushed route cannot be popped with browser-back, with the food-search screen exposing no back control to the accessibility tree at all — a dead end for a screen-reader user too, and worth fixing in the app.
- The store listing now uses all eight screenshot slots Play offers, up from five. The three added frames put a picture behind claims the copy already made and had nothing to show for: the 873-exercise library, the weight goal and trend chart, and saved meal templates. All three come from screens that already worked and simply had not been photographed. Two of them are opened by route (`/weight-tracking`, `/meal-templates`) rather than by clicking — `usePathUrlStrategy()` plus the dev server's index.html rewrite makes a deep link work, which is fewer steps to break and leaves no pushed route to escape. - `GET api/Meal` answers a missing `date` with 400 instead of throwing. The route takes a required `[FromQuery] DateTime`, and a non-nullable binding turns an omitted value into `0001-01-01`, which underflows `DateTime.MinValue` inside `MealDayWindow.ForRange` before any query is built — so a malformed request surfaced as a 500 and a stack trace. No user could reach it; the app always sends a date. Found by a script calling the endpoint by hand, and pinned by `MealControllerDateBindingTests`.
- The store screenshot pipeline now produces the two Play assets that are not screenshots — the mandatory 1024×500 feature graphic and the 512×512 icon — and `store/PLAY-CONSOLE.md` lays the whole listing out as the Play Console's own form, one copyable block per field with counts measured from the text rather than estimated. The earlier "~2,750 characters" for the full description was an estimate and wrong; it is 3,203 unwrapped.
- `store/screenshots/seed-screenshot-extras.mjs` completes existing sessions and logs sets against them rather than posting new ones. Posting new sessions on days the base seeder had already filled collided on `(workoutId, date)`, and the pull discards exactly that as a server-side duplicate, so none of them ever reached the device and Progress → Gym went on reading 1 workout. Two findings it could not work around are recorded rather than papered over: `SyncService` pushes logged sets and never pulls them back, so a reinstall or a second device loses set history and Exercise Progress starts empty; and today's meals render as "No foods added yet" although `api/Meal/all` returns them exactly as it returns every other day. See `docs/store-listing.md`.
- Recaptured the store screenshots against main at `30291b7`, now that `claude/food-search-meal-organization-5m043l` has merged. The food picker frame previously showed the pre-fix "Recently Added" — one flat list in row-id order — and now shows what that branch introduced: an "Eaten at this meal" group above "Other foods". This is the case the capture pipeline exists for. A drawn mockup would have gone on showing whichever list the person drawing it remembered; a capture had to be re-run against the merged code, and the change is visible in the diff of the PNG.
- Added `store/screenshots/seed-screenshot-extras.mjs`, which tops the seeded trainee up with completed training history and per-day calorie variation. It is deliberately separate from `e2e/tools/seed-review-data.mjs`, whose counts the Playwright suite asserts against — bending a test fixture to suit marketing artwork is how a fixture stops meaning anything. It also records a bug in that fixture's arithmetic: the one session it marks complete is dated `daysAgo(i - 2)` with `i === 0`, which is two days in the *future*, so Progress counted zero completed workouts on an account that looked fully populated everywhere else. Two things remain unresolved and are written down rather than papered over: Progress → Gym still reads 1 total workout and a 0-day streak even after eight completed sessions are posted across the last ten days, and still shows "No workout data yet" under Exercise Progress — most likely because those tiles count logged sessions with sets rather than scheduled workouts flagged complete, which is unconfirmed; and the Calorie Trend still draws a flat line, with the cause unestablished because `GET /api/Meal` returns 500 on this build. That 500 is worth a look on its own. See `docs/store-listing.md`.
- Found and documented, not yet fixed: the Trainer Console roster's Grid view (its default) renders each client's name, program, adherence and last session, none of which reaches a screen reader — not unlabelled, entirely absent from the accessibility tree. Table view, showing the same data, is unaffected. See `docs/frontend-design-review.md` section 14.
- The food search opened from a meal now orders "Recently Added" by that meal. Breakfast, lunch, dinner and snacks all showed the identical list in the identical order, because the list read the device's food library — which records no meal and no time — and sorted it by row id. The category the screen is opened with was used for the title and for the write, and never for the read, so a user logging breakfast scrolled past their lunch foods to reach their breakfast ones every morning. Foods previously eaten at the meal being logged now come first under their own heading, most recently eaten first, with everything else under a second heading; a meal with no history renders flat, with no headings, as before. The match is on food name rather than on `MealFoodTable.foodEntryId`, because adding a food from the recent list writes a *new* `FoodItem` row for that portion — the id in the meal is never the id on screen, so the obvious join returns nothing and reports no error. The client's `Snack`/`Snacks` fold now lives in one `MealCategory` helper mirroring the server's, which the Trainer Console's private copy delegates to. See `docs/recent-foods-by-meal.md`.

## 1.0.2+14

- Chat messages now show the time they were sent, and the day dividers in a thread name the right day. A message whose timestamp the server could not supply was being drawn as `01/01/0001` — the shape a missing date takes when a non-nullable field has to hold something — and a malformed one replaced the entire conversation with a load error. Timestamps are also read as the instants they are rather than as local wall-clock digits, so a payload without a timezone designator can no longer shift every message in the app by the reader's UTC offset. The day divider read its calendar fields off a UTC instant while the code deciding whether to insert one read local fields, so either side of local midnight the pill could announce a different day than the messages under it. Bubbles now carry a time, and a screen reader hears the full date and time on each one; a pending or failed message deliberately shows none, because the moment the user pressed send is not a sent time. See `docs/chat-timestamps.md`.
- The Trainer Console now opens in a fraction of the time. Four things were making a trainer watch a skeleton, and they compounded. The roster and the dashboard summary each looped over every client and read that client's *entire* training history — every session, exercise and logged set they had ever recorded — in order to count four weeks of them and find one date; because the two run in parallel, a single dashboard paint read the whole roster's history twice. Both are now one set of aggregate queries whose cost does not grow with the roster: for a trainer with 25 clients, 102 queries become 8. The other console reads had the same shape and are now bounded too — one day's workout history no longer reads a career, session review pages in the database instead of building every past session and keeping ten, and exercise names come from the exercises actually referenced rather than from loading the entire exercise catalogue. Reads no longer go through EF's change tracker, and three composite indexes cover the pairs these queries filter on. See `docs/trainer-console-loading.md`.

They were built together, so Dashboard, Messages, Workout Builder, Nutrition and Session Review each fired their own requests on the first frame — five screens' worth of network for the one the trainer was looking at. Each section now loads when it is first opened and stays loaded after that, so switching tabs is still instant. Chat is the exception and loads up front on purpose: it is what joins this device to every conversation, and deferring it would blank the unread badge.
- The dashboard now draws each part as it arrives instead of waiting for all of it. The client list and the summary tiles were behind one loading flag, so the list waited on the slower of the two and a single failed request blanked the whole page — including the invite button, the one thing an empty console is for. Client Detail behaves the same way now: a failing nutrition endpoint costs its own card rather than hiding the client's training.

- Fixed the strength progression chart on Client Detail showing blank exercise names. It looked names up by the wrong identifier, and a missing name rendered as an empty string rather than an error, so the failure looked like a design choice.

## 1.0.2+13

- The web bundle no longer fetches its rendering engine from Google's CDN at startup. `flutter build web` defaults to loading CanvasKit from `gstatic.com` at runtime rather than using the copy it just placed in the build output, so the uploaded bundle — the one the Trainer Console is served from — could not start on any machine that could not reach that domain, a corporate proxy with a strict allowlist included. Nothing caught it because no check the repo had ever loaded the bundle in a browser: `flutter analyze` reads source, `flutter test` runs widgets in a Dart VM with no bootstrap and no network, and `flutter build web` exits zero having written a URL into a JavaScript file. The build is now self-contained.
- Added end-to-end tests that run a real browser against the built web bundle in CI, which is how the above was found. Flutter web paints the entire app into a canvas, so the tests query the accessibility tree — the only surface a browser can see — which makes semantic labels on interactive widgets a testability requirement as well as an accessibility one. The suite also pins two rules that were previously only written down: that a signed-out visitor on web lands on login rather than the consumer welcome screen, and that unknown deep links are rewritten to the app shell while missing assets still 404. See `docs/e2e-playwright.md`.
- Registering a trainer account now opens the Trainer Console instead of the trainee dashboard, on every platform rather than only in a browser. Two things sent new trainers to the dashboard: the post-auth landing rule was written as a platform check (`kIsWeb`) rather than a role check, so off the web the role was never consulted and the console was reachable only from Settings; and the console's role gate treated "nobody has asked the server yet" as "not a trainer", which is exactly the state a brand-new account is in for the first second of its life. The gate now waits for the role to actually be answered — a cached answer for the same account counts, so returning users still see their own app immediately. Leaving the console for your own training is unchanged ("My training", no sign-out). See `docs/onboarding-and-roles.md`.
- Fixed cached access flags (trainer role, premium, assigned trainer) being restored for the wrong account when more than one person signs in on the same device. They were stored per device rather than per account, so the previous user's answers stood in for the next one's until the server replied — briefly granting a stranger's Pro, among other things. They are now keyed to the account they describe and ignored for anyone else.
- Fixed switching accounts on a device bringing workouts back wrong: exercises and sets duplicated, and exercises you had deleted restored. None of it was caused by the switch — those rows were already on the server. Removing an exercise from a workout that had already synced never reached the server at all (saving a workout did not mark it for re-upload, so the deletion sat in a queue nothing read), and retried uploads could leave a second copy of an exercise or a whole prescription behind. The app never noticed because it skips downloading any workout it already has; signing out clears the device, so the next sign-in was the first time it ever read the server's copy back. Deletions and edits now reach the server, repeat uploads no longer create a second copy, and the download folds together any duplicates already stored — so affected accounts read correctly with no re-save and no cleanup. See `docs/sync-account-switch-duplication.md`.
- Fixed the app taking hours to fetch an account's data after signing in again. The daily background task only uploads, but it stamped the same "last synced" marker the startup download checks, so a background upload could suppress the download for six hours. The two are now tracked separately.
- Signing out now clears this device's copy of your account immediately, rather than at the next sign-in. If anything has not reached the server yet, ForgeForm tries to upload it first and then says how many changes would be lost and lets you cancel.
- Deleting a workout you had ever scheduled failed on the server with an error the app never surfaced, so the workout came back on the next full download. It now deletes, along with any sessions of it you never performed; a workout with training logged against it is kept, and the app is told why instead of retrying forever.
- Trainer Console: the Nutrition tab no longer shows a client's day twice over — two breakfasts, two lunches, two dinners, two snacks. The database has never limited a client to one meal row per category per day, and the app's sync could genuinely write a second one (a reconcile pass clearing a meal's server link when the row only looked gone, a response lost after the row was written, a second device, or the old `Snack`/`Snacks` category spelling failing to match itself). None of it was visible in the app, which renders four fixed meal sections and reads the first row of each, and the day's calorie and macro totals are computed from the foods themselves, so folding the rows back together leaves them unchanged. Creating a meal is now idempotent per day and category, so no new rows accumulate, and the console folds rows that already exist back into one meal — no re-sync or cleanup needed on affected accounts. See `docs/trainer-nutrition-duplicate-meals.md`.
- Trainer Console: Snacks in the Nutrition tab now carry the snack icon and sort between lunch and dinner instead of last. The screen matched the lowercase `snack` its API documents while the app writes `Snacks`, so the category fell through to the unknown-category handling everywhere except its label.

## 1.0.2+12

- Trainer Console: Session Review no longer lists sessions from workout plans the client has moved off. Activating a new plan only deactivates the old one — every date it ever generated stays scheduled — so the trainer's history was padded with dates nobody had asked the client to train on, each shown as Missed. Sessions the client actually completed, skipped or logged against are kept regardless of what became of the plan. The same filter now applies to average adherence, per-client roster adherence and the 12-week attendance chart, all of which were counting those dates as planned-and-not-completed and so understating adherence.
- Trainer Console: Session Review no longer shows exercises that are no longer in the workout, previously listed as Skipped. Removing an exercise from a workout failed server-side for any workout that had ever been scheduled (a restricted foreign key from the logged-session tables), so the exercise stayed in the workout on the server and was stamped onto every session generated afterwards, invisible in the app but visible to the trainer. Removal now works: sessions that logged nothing against the exercise lose it outright, and where sets were logged the exercise is retired from the workout instead of deleted, so the history keeps its name. See `docs/trainer-session-review.md`.
- Trainer Console: Session Review no longer inflates how many sets an exercise prescribes. Saving a workout pushes its whole prescription, and the API appended it instead of replacing it, so an exercise saved three times reported three times as many sets. The API now replaces, and Session Review collapses duplicate set numbers so already-affected workouts read correctly without being re-saved.
- Trainer Console: tapping a meal in the Nutrition tab now opens it, listing every food in that meal with its own serving weight, calories and macros. The meal row only ever had space for a one-line list of names, so which item carried the calories wasn't visible anywhere. The nutrition endpoint now returns per-food nutrition alongside the names it already sent; a meal with no per-food detail stays a plain, non-tappable row.
- Fixed the Trainer Console's Nutrition tab failing with "Could not load this client's nutrition" for every client on every date, and Client Detail failing with it. The nutrition endpoint passed the requested day to Postgres without a UTC kind, which Npgsql rejects outright for a `timestamp with time zone` column, so the request 500'd before it read anything. Client Detail loads its three panels together, so the same error blanked that screen too.
- Fixed the trainer-facing nutrition day being off by one for any client not in UTC. Meals are logged against the client's local midnight and stored converted to UTC, so a German client's Tuesday sits at 22:00 Monday in the database; the summary read midnight-to-midnight in UTC and so reported the wrong day's food. Days are now matched against the day they were logged on. Clients at UTC+13/+14 (New Zealand in summer, Samoa, Kiribati) still read one day early.
- The 7-day nutrition trend now loads in a single query instead of seven sequential ones.
- Trainer Console nutrition and client-detail failures are now logged with their cause instead of being swallowed, which is why the above went unnoticed.

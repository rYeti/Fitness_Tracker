# Chat: how it works and why

A walkthrough of the chat feature as built, written to be read on its own. It
covers the two backend defects that had to be fixed first, the delivery
guarantee the client is built around, and the handful of decisions that are not
obvious from the code.

Line references are to the commit that introduced this document.

---

## 1. The backend was broken, and neither bug was visible to the compiler

`chat-feature-roadmap.md` described the backend as shipped. It could not work.
Both defects share a cause: the code was written against a mental model of the
schema rather than the schema itself, and C# had nothing to say about either.

### 1a. The message that could never be stored

`ChatMessage` (`FitTracker.Api/Models/ChatMessage.cs`) does not carry a trainer
id and a client id. It carries `TrainerClientId` — a foreign key to the
*relationship* row:

```
TrainerClients (Id, TrainerId, ClientId, Status, …)
      ▲
      │ TrainerClientId   non-nullable FK, cascade delete
ChatMessages (Id, Body, SenderId, SentAt, TrainerClientId, …)
```

That indirection is good design. A message belongs to a relationship, so
revoking one cascades its messages away, and there is exactly one place that
decides whether a pair may talk. But it also means you cannot insert a message
without first turning a `(trainerId, clientId)` pair back into a relationship id.

`ChatService.SendMessageAsync` received those two loose Guids and built the
entity straight from them, never assigning `TrainerClientId`. It stayed
`Guid.Empty`, matched no row in `TrainerClients`, and Postgres rejected every
insert. **Every send failed.**

The tell that this was an oversight rather than a design choice: `ChatService`'s
constructor already took `ITrainerClientRepository` and never used it, and the
method it needed — `GetActiveRelationshipAsync(trainerId, clientId)` — already
existed on both the repository and the service interface. The fix is three lines
(`ChatService.cs:20`), but you cannot find it by reading `ChatService` alone,
because `new ChatMessage { … }` compiles perfectly with the field missing.

### 1b. The history that was always empty

`IChatService.GetChatHistoryAsync(Guid trainerId, Guid clientId, int range)`.
The controller called it as `GetChatHistoryAsync(actualClientId, trainerId, range)`
— the first two arguments the wrong way round. Both are `Guid`, so it compiled.

Downstream, the repository filters:

```csharp
c.TrainerClient.TrainerId == trainerId && c.TrainerClient.ClientId == client
```

Swapped, that asks for the relationship whose trainer is this client and whose
client is this trainer. Never true. The endpoint returned `200 OK` with `[]`,
forever.

This is the one that would have cost the most debugging time on the Flutter
side, because an empty list is indistinguishable from "this pair has never
spoken" — you would naturally go hunting in the client first.

**The general lesson: consecutive same-typed positional parameters are a trap.**
Two `Guid`s in a row with no compiler protection. Note that `ChatHub.SendMessage`
gets the same call right, and it does so by deriving and *naming* `actualClientId`
before passing anything. Naming intermediate values is what kept the hub correct.

`range` had the same shape of problem in miniature: no default, so an omitted
query parameter bound to `0` and `Take(0)` returned nothing — again looking
exactly like an empty thread. It now defaults to 50 and is clamped
(`ChatController.cs:43`).

### 1c. Dedup that trusted an id too far

`AddMessageAsync` looked up an existing message by `Id` alone. Message ids are
generated by the *client* (see §2), so this is the one code path that returns a
row the caller did not write. Scoped to the pair now, with a mismatched id
rejected outright (`ChatRepository.cs:24`). Guessing a v4 UUID is impractical, so
this is defence in depth rather than a live hole — but it costs one `AND`.

## 2. The outbox, and why it exists

This is the conceptual heart of the feature, and it generalises well beyond chat.

You call `SendMessage` over a socket. The connection dies before you get a reply.
Did the server receive it?

**You cannot know.** Both outcomes look identical from the client:

| What actually happened | What the client observes |
| --- | --- |
| The server never got the frame | `invoke()` never completes |
| The server stored it, the ack was lost coming back | `invoke()` never completes |

And guessing is lossy in *both* directions:

- Assume "never arrived", skip the resend → the message silently vanishes.
- Assume "arrived", skip the resend → the message silently vanishes differently.

Either way the user watches their message disappear, which is the worst failure a
messaging app has.

So the design refuses to guess:

1. **Always resend.** The client's job is delivery, not deduplication.
2. **Push "was this already stored?" to the only party that knows** — the server.
3. **Make that question answerable** by generating the id on the client, before
   the first attempt, so a retry carries the same identity as the original.

Point 3 is why `messageId` is client-generated. If the server assigned ids, a
retry would be a brand-new message from its point of view and you would get
duplicates. Because the id comes from the client and never changes across
attempts, the server's lookup converges both branches on one outcome: exactly one
row, and the client marked sent.

This property is **idempotency**, and the pattern — client-generated key plus
server-side dedup on that key — is the standard way to make at-least-once
delivery behave like exactly-once. Stripe's idempotency keys work identically,
for identically the same reason.

The Drift outbox table is just where the not-yet-acknowledged set is persisted so
it survives an app restart. Its three states map onto the three things that can
be true:

| State | Meaning | Who resolves it |
| --- | --- | --- |
| `pending` | No ack. Might have landed, might not. | The reconnect loop |
| `sent` | Acked. The server row is authoritative from here. | — |
| `failed` | The retry budget is spent. | The user, manually |

`failed` exists **only on the client**. The server has no concept of it, because
from its side nothing ever arrived to fail. That is exactly why it is the one
state needing a visible "tap to retry": the automatic loop has already given up.

## 3. Why replay is sequential, and ordered by the outbox

`replayPending` (`chat_repository.dart:253`) resends one message at a time,
awaiting each ack before starting the next. `Future.wait` would be faster. Don't.

SignalR guarantees ordering *within* one invocation, not *across* concurrent
ones. Three messages sent in parallel can be stored in any order, each stamped
with whenever the server happened to process it. The user typed "did you see my
form?", "on the last set", "the video's attached" — and reads back something that
means something else. In a conversation, the order *is* the meaning.

For the same reason replay stops at the first failure rather than skipping ahead:
sending a later message while an earlier one is still queued reorders the thread.

The sort key is the outbox's `createdAt` — the moment the user pressed send on
*this device* — not the server's `SentAt`. The user's own intent order is what
they expect to see.

## 4. Your own message arrives twice

`ChatHub.SendMessage` does two things: it returns the persisted DTO to the
caller, *and* it broadcasts to the group — a group the sender is in. So a sender
with the thread open receives the same message down two paths:

```
invoke('SendMessage') ────────► ack (return value)   ┐
                                                     ├─► same message, twice
hub broadcast ──► on('ReceiveMessage') ──────────────┘
```

A UI that appends everything from `ReceiveMessage` shows the sender their own
bubble twice.

**The fix belongs in the repository, not the widget** (`chat_repository.dart:302`).
The repository already knows every id in the thread — from history, from the
outbox, from acks — so it can filter the incoming stream before the provider sees
it. Putting the dedup in a widget would mean re-implementing it in the console
screen, the trainee screen, and every surface after that. Fix data problems at the
data layer; that is the whole reason `incomingFor()` returns a stream instead of
exposing the raw hub callback.

Broadcasting to the sender is worth keeping, incidentally: it is what makes the
trainer's phone show the message they just sent from their laptop.

## 5. "Is this message mine?" without knowing who you are

The natural implementation is `isMine = senderId == currentUserId`. That is not
available here. `AuthResponseModel` stores a token, username, email, names and an
expiry — **no user id**. And `AccessProvider.initialize` is called with
`userId: restoredAuth.user!.username`, the username standing in for an id
(it feeds RevenueCat's appUserID, where any stable string works). There is no
server UUID for the signed-in user anywhere on the client.

Three ways out:

1. Decode the JWT payload and read the `nameidentifier` claim. Works, but means
   hand-rolling base64 JWT parsing and trusting token internals for UI logic.
2. Add the id to the auth response. Correct long-term, but it touches the auth
   DTO, the secure-storage payload and session restore — a wide blast radius for
   a chat feature.
3. Notice that a thread has exactly two parties, and the DTO names both.

Option 3 is what shipped (`thread_message.dart:56`):

```dart
isMine: message.senderId != otherPartyId
```

`otherPartyId` is the client's id on the console and the trainer's id in the
trainee app. Nothing else is needed — and it has a much better side effect than
brevity: **the entire repository and provider layer becomes role-agnostic**, which
is precisely what lets one implementation serve both surfaces. The trainee screen
is the console's logic with a different id passed in.

It is also the same concept the outbox's `otherPartyId` column already encoded
("this device's view of one thread"), so the model stays consistent end to end.

If the auth response ever grows a real user id, option 2 becomes strictly better
and the change is one line. Building it now would have been speculative work for
no current benefit.

## 6. Why `ThreadMessage` is a third model

There are two types describing "a message": `ChatMessage` (exists on the server)
and `ChatOutBoxTableData` (a send attempt this device is tracking). They stay
separate on purpose — a message being typed has no `sentAt` and may never get one,
and collapsing them produces a type where half the fields are nullable and no
reader can tell which combinations are legal.

But the UI has to render one ordered list containing both. Giving widgets two
shapes to branch on pushes merge logic into `build()` methods, where it gets
duplicated per screen. So the repository projects both into one presentation type:

```
ChatMessage (server)        ─┐
                             ├─► ThreadMessage { messageId, body, timestamp,
ChatOutBoxTableData (local) ─┘                   isMine, status, … }
```

`ChatBubble` takes a `ThreadMessage` and knows nothing about where it came from.
The merge — sort by timestamp, dedupe by id — lives in exactly one function.

## 7. The package hunt, and a lesson about pub.dev

The roadmap suggested `signalr_netcore`: 77,000 downloads a month, 232 likes,
actively maintained. It is unusable here.

Its `lib/web_socket_transport.dart` opens with `import 'dart:io' as io;` —
unconditionally. Dart compiles to two very different runtimes: native (`dart:io`:
real sockets, files, processes) and web (JavaScript: no sockets, only browser
APIs). A package that works on both must **conditionally import** the
platform-specific half, which `signalr_hub` does:

```dart
import 'web_socket_channel_stub.dart'
    if (dart.library.js_interop) 'web_socket_channel_web.dart'
    if (dart.library.io)         'web_socket_channel_io.dart';
```

The compiler picks a branch per target, so `dart:io` never reaches the JS build.
`signalr_netcore` has no such fallback, that file is reachable from its public
API, and `flutter build web` therefore fails outright. Since `CLAUDE.md` makes web
the Trainer Console's primary delivery surface, that rules it out entirely.

This is also why pub.dev lists its platforms as android/ios/linux/macos/windows
with **web absent** — those badges are computed from exactly this analysis.

> **Check the platform badges before the popularity score.** The most popular
> package in an ecosystem is often the one written before that ecosystem cared
> about the browser.

The field, once filtered on web support:

| Package | Web | Last published | Adoption | Blocker |
| --- | --- | --- | --- | --- |
| `signalr_netcore` 1.4.4 | ✗ | Sep 2025 | 77k/mo | unconditional `dart:io` |
| `signalr_core` 1.1.2 | ✓ | Feb 2024 | low | needs `web_socket_channel ^2`, tree is on 3.0.3 |
| `signalr_netcore3` 1.3.8 | ✓ | Dec 2023 | 56/mo | same `web_socket_channel` conflict |
| `signalr_core_new` 1.0.3 | ✓ | Nov 2024 | 149/mo | no repository link, unknown maintainer |
| **`signalr_hub` 2.1.0** | ✓ | Aug 2026 | 238/mo | very new |

`signalr_hub` won on the only hard constraints — web support and a dependency
graph that resolves. Its newness is a real risk, mitigated by §8.

### Sizing the `get_it` bump

`signalr_hub` requires `get_it ^9.2.1`; the app pinned `^8.0.0`. A major bump
sounds alarming. Three steps to find out:

1. **Read the changelog for the major release.** get_it 9.0.0 has exactly one
   breaking change: disposal order is now strict LIFO, and `strictDisposalOrder`
   was removed from `reset()`, `resetScope()`, `popScope()`, `popScopesTill()`,
   `dropScope()`.
2. **Grep for that API surface:**
   `strictDisposalOrder|\.reset\(|popScope|dropScope|resetScope|pushNewScope`
3. **Read the hits.** All three `.reset(` matches were `AccessProvider.reset()` —
   our own class, nothing to do with GetIt.

So the "major bump" is a one-line pubspec edit. The app only ever calls
`registerLazySingleton`, `registerSingleton` and `sl<T>()`, none of which changed.

One further hazard, checked and cleared: a package registering into
`GetIt.instance` would collide with this app's `sl` (also `GetIt.instance`), and
whichever registered second would throw. `signalr_hub` declares
`final GetIt signalRLocator = GetIt.asNewInstance();` with the comment "Dedicated
GetIt scope for this package so host apps are not polluted." Worth verifying
rather than assuming for any package that depends on a service locator.

## 8. Why `ChatSignalRClient` stays an interface

`SignalRHubChatClient` is the only file that imports `signalr_hub`. Everything
else depends on the abstract `ChatSignalRClient`, described in our vocabulary:
`connect`, `joinGroup`, `send`, `incomingMessages`, `onReconnected`,
`connectionStatus`.

The obvious payoff is insurance: a two-week-old package with 238 downloads a month
can be swapped by rewriting one file.

The payoff that matters daily is testing. Every state this feature has to get
right is a state a real socket will not produce on demand:

- a send that never resolves
- a send that throws after the server already stored the message
- a reconnect firing at one exact moment
- the same message arriving twice

Against a real connection these are close to untestable. Against
`FakeChatSignalRClient` each is a line:

```dart
signalR.holdSend = Completer<void>();   // freeze a message in flight
signalR.throwOnSend = StateError('…');  // lose the ack
signalR.failFirstNSends = 1;            // a bounded outage
signalR.fireReconnected();              // reconnect, now
```

That is the real argument for interfaces at I/O boundaries, and it is why the seam
sits here rather than at some more abstract "service" layer: **this is precisely
the boundary where nondeterminism enters the system.**

## 9. Read state is two columns

Unread is per-viewer. The trainer's unread count for a thread and the client's are
different numbers over the same rows. `TrainerClients` holds **one row per pair**,
so a single `LastReadAt` would be written by both sides, and whoever opened the
thread last would silently clear the other's badge.

Hence `TrainerLastReadAt` and `ClientLastReadAt`, with the endpoint stamping
whichever side the caller resolves to — reusing `ResolveTrainerAsync`, the same
symmetry helper the hub and controller already use to serve both roles from one
code path.

The count (`ChatRepository.cs:81`):

```
messages where SentAt > <caller-side>LastReadAt and SenderId != callerId
```

**The `SenderId != callerId` term is the subtle one.** Without it, your own
messages count as unread to you — they were all sent after you last read the
thread. It is the kind of bug that only shows up once someone replies and
immediately sees a badge on their own conversation.

Storing a timestamp rather than a per-message read flag is the cheap choice and
the right one: O(1) to write, no join table, and it answers the only question the
UI asks ("how many since I looked?"). Per-message rows would only be needed for
per-message receipts, which are out of scope.

The unread query is expressed as boolean algebra rather than a `CASE` expression
on purpose — a conditional inside a correlated aggregate is the kind of thing
providers translate inconsistently, and this has to run on both Npgsql and the
Sqlite the tests use.

## 10. The seven states a chat screen has

`CLAUDE.md` requires loading / empty / error / populated on every data-bound
screen. Chat adds three more that exist *because of* the reliability design:

| State | Driven by | Treatment |
| --- | --- | --- |
| Loading | `isLoading` before history lands | skeleton bubbles, not a spinner |
| Empty | history + outbox both empty | "No messages yet — say hello" |
| Error | history fetch threw | inline message + retry |
| Populated | the merged thread | the normal list |
| Sending | outbox row `pending` | dimmed + clock icon |
| Failed | outbox row `failed` | "Failed to send — tap to retry" |
| Reconnecting | transport status | thin banner |

The last three are the user-visible surface of §2's state machine. Skipping them
turns a correct implementation into one that *looks* broken: a message that
vanishes for two seconds and reappears, or silence on a flaky line with nothing
to explain it.

Two details worth keeping:

- **The bubble appears before the network call, not after it.** `sendMessage`
  reports the queued message through a callback the moment it is durably in the
  outbox (`chat_repository.dart:160`), and again when the wire call settles. Both
  updates carry the same id, so the provider's `_upsert`
  (`chat_provider.dart:137`) replaces rather than appends. Waiting on the returned
  Future would leave the composer looking dead for as long as the request takes —
  which, on the connection this whole design exists for, can be forever.
- **Status is never colour alone.** The unread badge shows a number, the failed
  marker pairs red with an icon and words, the connection banner names what is
  happening. Colour-only status fails for colourblind users, and "red bubble"
  tells nobody what to do about it.

## 11. Test infrastructure, and one provider choice that mattered

The API had **no test project at all** before this work; `FitTracker.sln`
contained one project. That is not unrelated to §1 — nothing ever exercised
`ChatService` before production did.

`FitTracker.Api.Tests` runs on **`Microsoft.EntityFrameworkCore.Sqlite` against an
open in-memory connection**, not `EntityFrameworkCore.InMemory`. This matters more
than it looks:

> **The InMemory provider does not enforce foreign keys.** The test asserting that
> a sent message is persisted would have passed against the broken code in §1a.

Sqlite enforces them, so the bug is observable from a test. Two supporting
details: the connection is held open for the fixture's lifetime (an in-memory
Sqlite database is destroyed when its last connection closes), and the schema
comes from `EnsureCreated()` rather than the real migrations, which are
Npgsql-specific (`uuid`, `timestamp with time zone`) and will not run on Sqlite.
That means the fixture tests the EF model, not the migration history — migrations
are verified by the deploy running them.

CI now builds and tests the API on pull requests (`.github/workflows/api.yml`).
Previously `deploy.yml` ran only on `main`, so the first thing to exercise an API
change was production.

## What is deliberately not here

- **Media and attachments.** The DTO has the fields, but there is no upload
  endpoint. The composer shows a disabled attachment affordance rather than
  hiding it, so the layout doesn't shift when it starts working.
- **Typing indicators and sender-visible read receipts.** Each needs its own hub
  methods and schema.
- **Push notifications for a backgrounded app.**
- **Retry backoff tuning.** `maxReplayAttempts` is 3 with no delay between
  reconnects, because the reconnect itself is the backoff. How many attempts, and
  whether to space them, is a product decision nobody has made yet.
